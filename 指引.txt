# 1. 项目研究背景

项目关注 long-horizon GUI / computer-use agent 的纠错问题。

DEVICESWORLD 的实验表明，当前 Agent 的失败并不只是单步 action 错误，还包括：

* 漏掉必要 subgoal；
* source / target device 或 location 混淆；
* 最终结果存在但内容错误；
* action 已经执行，但结果没有真正 persistence；
* 多个设备或 endpoint 各自取得局部进展，但最终条件没有 jointly satisfied；
* 局部失败后持续重复操作，无法识别真正的错误来源。

论文的核心观察之一是：

> **Local progress does not imply end-to-end completion.**

GUI-SAGE 则主要研究：

> 在 action 真正执行之前，Monitor 是否应该批准该 action、返回 corrective feedback，或者升级到更强 Mentor。

其核心属于：

> **pre-execution action-level verification / routing。**

我们的项目不要退化成：

```text
GUI-SAGE + memory
```

或：

```text
action critic + retry
```

---

# 2. 我们的核心 Research Question

GUI-SAGE 主要回答：

```text
Should this proposed action be executed?
```

我们的项目回答：

```text
When execution becomes inconsistent with the task,
which task-state dependency was first violated,
which downstream progress is therefore no longer trustworthy,
and what is the minimum repair required to restore consistency?
```

核心研究对象从：

```text
Action-level correction
```

提升为：

```text
Task-state-level causal repair
```

整个代码设计必须服务于：

```text
task inconsistency
        ↓
causal fault localization
        ↓
identify corrupted dependency
        ↓
invalidate affected descendants
        ↓
preserve unrelated verified progress
        ↓
minimal repair
        ↓
re-verification
```

---

# 3. 项目核心 Hypotheses

所有代码最终应该能够支持验证以下假设。

## H1 — Causal Fault Localization

显式维护 dependency-aware task state，是否能够比“检查最近一步 action”更准确地定位真正错误根因？

---

## H2 — Minimal Repair

发生错误以后，能否只修复受影响的 task-state dependency，而不是重新执行整个任务或固定回退若干步？

---

## H3 — Progress Preservation

发生错误以后，能否保留与错误无关、此前已经验证正确的执行进度？

---

## H4 — End-to-End Recoverability

更准确的 fault localization 和更小的 repair scope，最终是否能够提高任务 recovery success？

---

# 5. StateGuard 的三项核心能力

## 5.1 Verify

根据：

```text
task state
previous observation
proposed action
expected effect
new observation
```

判断：

```text
VERIFIED
CONTRADICTED
UNKNOWN
```

不能只使用：

```text
correct / wrong
```

因为真实环境中经常无法从当前 observation 判断操作是否真正生效。

例如：

```text
Click Save
```

并不能直接意味着：

```text
file saved successfully
```

必须重新获得 evidence。

---

## 5.2 Localize

当出现 inconsistency 时，找到：

> earliest violated task-state dependency / causal root

例如：

```text
S1 acquire date            VERIFIED
 ↓
S2 open workbook           VERIFIED
 ↓
S3 select Sheet2           FAILED
 ↓
S4 write value             STALE
 ↓
S5 save file               STALE
```

如果最后发现值被写到了 Sheet1：

```text
fault_root = S3
```

而不是最近的：

```text
S5 save
```

---

## 5.3 Repair Minimally

当：

```text
fault_root = S3
```

系统只 invalidate：

```text
S3
+
dependent descendants(S3)
```

而保留：

```text
independent VERIFIED nodes
```

StateGuard 本身不负责执行 repair GUI action。

它只生成：

```text
RepairRequest
```

由原 Executor 完成实际修复。

# 7. 核心 Schema

## 7.1 NodeStatus

实现：

```python
class NodeStatus(str, Enum):
    PENDING = "pending"
    ACTIVE = "active"
    EXECUTED = "executed"
    VERIFIED = "verified"
    FAILED = "failed"
    STALE = "stale"
```

必须严格区分：

```text
EXECUTED != VERIFIED
```

### 状态含义

`PENDING`

尚未开始。

`ACTIVE`

当前正在处理。

`EXECUTED`

已经执行相关 action，但没有充分 evidence 证明结果正确。

`VERIFIED`

有明确 evidence 支持当前 subgoal 已正确完成。

`FAILED`

当前 node 自身已经发现 contradiction。

`STALE`

node 自身结果未必错误，但其上游 dependency 已失效，因此不能继续认为它可信。

# 11. DependencyGraph

不要让 LLM 自由决定 affected nodes。

LLM / heuristic 只负责：

```text
fault_root
```

之后 downstream invalidation 必须使用 deterministic graph code：

```python
affected = graph.descendants(fault_root)
```

要求实现：

```python
parents(node)
children(node)
ancestors(node)
descendants(node)
topological_order()
validate_acyclic()
```

# 12. Fault Propagation

如果：

```text
fault_root = S3
```

则：

```text
S3 → FAILED
```

其 descendants：

```text
VERIFIED
EXECUTED
ACTIVE
```

统一转为：

```text
STALE
```

不要直接全部：

```text
FAILED
```

因为 downstream node 不一定自身执行错误，只是其依据已经不可信。

---

# 13. Causal Root 定义

当前版本采用：

> The earliest task-state node whose expected condition is contradicted or unsupported while its prerequisite dependencies remain valid.

候选节点必须优先满足：

```text
parents == VERIFIED
```

如果多个 candidate：

优先选择：

1. 有直接 contradiction 的 node；
2. transition mismatch 明显的 node；
3. 能解释最多 downstream failures 的 node；
4. verified evidence 最弱的 node；
5. 更靠近 failure source 的 node。

第一版可以规则实现。

后续再考虑 learned localizer。

# 17. FINISH Rule

不要设计额外 Global Commit Agent。

实现：

```python
def can_finish(task_state):
    return all(
        node.status == NodeStatus.VERIFIED
        for node in task_state.nodes.values()
        if node.required
    )
```

如果任何 required node：

```text
PENDING
ACTIVE
EXECUTED
FAILED
STALE
```

则：

```text
FINISH rejected
```

StateGuard 返回 missing / repair information。

# 18. Runtime 核心接口

最终核心代码必须可以写成：

```python
task_state = compiler.compile(task)

obs = env.reset()

repair_context = None

while True:

    proposal = executor.act(
        observation=obs,
        task_state=task_state,
        repair_context=repair_context,
    )

    if proposal.is_finish:

        result = guard.verify_finish(
            task_state=task_state,
            observation=obs,
        )

        if result.approved:
            break

        repair_context = result.repair
        continue

    before = obs

    after = env.step(proposal.action)

    result = guard.verify_transition(
        task_state=task_state,
        before=before,
        proposal=proposal,
        after=after,
    )

    task_state.apply(result.state_updates)

    if result.requires_repair:
        repair_context = result.repair
    else:
        repair_context = None

    obs = after
```

整个项目未来无论如何扩展，都尽量不要破坏这个 API。

# 20. UNKNOWN 状态处理

如果：

```text
action executed
```

但无法确认 effect：

```text
judgement = UNKNOWN
```

不要：

```text
mark VERIFIED
```

也不要立刻：

```text
mark FAILED
```

而应该产生：

```text
verification target
```

例如：

```text
Re-open the saved file to confirm persistence.
```

这一机制后续可用于解决“action 已发出但结果未真正保存”的问题。

# 40. 最终原则

整个 Phase I 的核心不是：

> build a powerful GUI agent

而是：

> **build a clean, testable task-state repair mechanism.**

始终围绕三个概念：

```text
1. Fault Localization
2. Progress Preservation
3. Minimal Repair
```

如果某项功能不能直接帮助这三件事，暂时不要加入。

最终系统应该能够用一句话描述：

> **StateGuard maintains an explicit verified task state, identifies the earliest violated dependency when execution becomes inconsistent, invalidates only the downstream progress affected by that violation, and provides a minimal repair target while preserving independent verified progress.**
